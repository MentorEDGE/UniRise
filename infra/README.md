# UniRise infrastructure (dev)

Terraform code for the shared **dev** environment on AWS (region `ap-south-1`, Mumbai), plus the local Docker setup in the
repo root. Decisions: ARCHITECTURE.md ADR 14. Status: **written and syntax-checked with OpenTofu (`validate`); never planned or
applied against AWS.** Read the plan output before you apply anything.

## What it creates
| Piece | Details |
|---|---|
| Network | One VPC, two public and two private subnets, free S3 endpoint. **No NAT gateway** (it would cost more than everything else). |
| Database | RDS PostgreSQL 16, `db.t4g.micro`, 20 GB gp3, encrypted, private, single-AZ, 7-day backups. The master password is generated by RDS and kept in Secrets Manager; it is never in code or state. This one instance will hold several databases (the control plane and one per test tenant, see rms-docs/MULTI_TENANCY_DESIGN.md §13), created by the application, not by Terraform. |
| Bastion | Optional `t4g.nano` with no inbound ports, reached only through SSM. Its network egress is limited to PostgreSQL to the database and HTTPS. A custom SSM document (`unirise-dev-db-tunnel`) fixes the tunnel's target to the database, so developers cannot forward to other hosts or ports. |
| Storage | S3 buckets `uploads` (versioned) and `exports` (objects expire after 30 days). Private, encrypted, TLS only. |
| Email | SES sender identity and configuration set. **SES starts in sandbox mode**: it can only send to addresses you verify. |
| Registry and logs | ECR repository `unirise-backend` (scan on push), CloudWatch log group `/unirise/dev/app` (14 days). |
| Access | IAM groups `unirise-developers` and `unirise-admins`, MFA required for both. Developers sign in to the database with **IAM authentication as a limited user**; they cannot read the master password. |
| Cost guard | Monthly budget limited to resources tagged `Project=UniRise`, with email alerts at 80% and 100% forecast. |

Rough running cost: about US$20 to 40 a month (the database and bastion dominate). Check the AWS pricing calculator; I have not priced it.

## Things you must know first
- **The AWS account is shared with other projects.** Everything here is named `unirise-dev-*` and tagged `Project=UniRise`, and developer permissions only cover those resources. Admins get **AdministratorAccess to the whole account**, so add as few as possible.
- Nothing here creates a **domain**. The planned `unirise.mentoredge.co.in` comes later. DNS for `mentoredge.co.in` is managed in Hostinger, so the later steps are: add the records AWS asks for in Hostinger (SES domain verification, DKIM, the certificate validation, and a CNAME to the load balancer).
- Users are created **without passwords or access keys**, so no secret lands in Terraform state. Give console access yourself: `aws iam create-login-profile --user-name <name> --password-reset-required --password '<temporary>'`, share the temporary password privately, and ask them to set up MFA at first sign-in. Switching to IAM Identity Center later is better for a bigger team.
- Keep real researcher data out of dev.

## First time
```bash
aws login                                   # your current session has expired
export AWS_PROFILE=default AWS_REGION=ap-south-1
aws sts get-caller-identity                 # check this is the right account

cd infra/bootstrap                          # one-time: the bucket that holds Terraform state
terraform init && terraform apply           # note the bucket name it prints

cd ../envs/dev
cp backend.hcl.example backend.hcl          # put your account id in the bucket name
cp terraform.tfvars.example terraform.tfvars  # set budget_email, admins, developers; leave ses_sender_email empty until the domain is verified
terraform init -backend-config=backend.hcl
terraform plan                              # read it
terraform apply
```
`tofu` works the same as `terraform` if you prefer OpenTofu.

After apply:
1. Open the SES verification email sent to `ses_sender_email` and click the link.
2. To send to real users, ask AWS to move SES out of the sandbox (SES console, Account dashboard).
3. **Once, an admin creates the database logins** (developers cannot do this). Open the tunnel with `db_tunnel_command`, connect as `unirise_admin` with the master password from the Secrets Manager secret named by `rds_secret_arn`, and run:
   ```sql
   -- for developers: IAM sign-in, connect to the control-plane database only
   CREATE USER unirise_dev;
   GRANT rds_iam TO unirise_dev;
   GRANT CONNECT ON DATABASE unirise TO unirise_dev;

   -- for the API: may create institution databases, but is not a superuser (tested in NonSuperuserTest)
   CREATE ROLE unirise_app LOGIN PASSWORD '<generate one, do not reuse>' CREATEROLE CREATEDB;
   GRANT pg_signal_backend TO unirise_app;
   ALTER DATABASE unirise OWNER TO unirise_app;
   ```
   Store the `unirise_app` password in Secrets Manager yourself (`aws secretsmanager create-secret --name unirise/dev/app-db ...`) so it never enters Terraform state. The control-plane database is `unirise`, the one RDS creates. The master user is for admins only; never hand its password to developers.
4. **Developers** open the tunnel with `db_tunnel_command` (it listens on `localhost:15432`) and connect with `db_connect_command`, which signs in with a 15-minute IAM token instead of a stored password. It needs the AWS CLI, the Session Manager plugin and `psql`.

## Running the API against this database
Set `CONTROL_DB_URL=jdbc:postgresql://<rds_endpoint>:5432/unirise?sslmode=require`, `CONTROL_DB_USER=unirise_app`, `RMS_DB_PASSWORD` from the secret, `TENANT_DB_HOST=<rds_endpoint>` and `TENANT_DB_JDBC_PARAMS=sslmode=require` (RDS forces TLS). From a laptop use the tunnel (`localhost:15432`) for the first two instead of the endpoint, but keep `TENANT_DB_HOST` as the real address when the API runs inside AWS.
`sslmode=require` encrypts but does not verify the server; move to `verify-full` with the RDS CA bundle before real data.

## Domain (DNS stays in Hostinger)
Set `domain_name = "dev-unirise.mentoredge.co.in"` (the dev website) and apply; the API host defaults to `api.dev-unirise.mentoredge.co.in`. `dev-unirise` is only a record inside the `mentoredge.co.in` zone (it has no zone of its own, and the "external domain" entry in hPanel cannot take records: it says "Domain not found"), so add every record under **Domains > mentoredge.co.in > DNS records** and type the name relative to `mentoredge.co.in`, ending in `.dev-unirise` (for example `api.dev-unirise`). Terraform creates the certificate for the API host and the SES domain identity, then `tofu output dns_records` lists the CNAME records. Add them in the Hostinger DNS panel, check them with `dig CNAME <name>`, and wait for the certificate to show Issued and SES to show verified. A CNAME cannot share a name with another record, so check the names first. The record for the load balancer is added later, when the ECS stage exists.

## Local Docker
```bash
cp .env.example .env          # in the repo root; set local-only passwords
docker compose up -d          # PostgreSQL 16, MinIO (S3-compatible), Mailpit; all on 127.0.0.1
```
Use the local services for daily coding and the AWS dev environment for shared testing and deploys.

## Adding a developer
Add their sign-in email to `developers` in `terraform.tfvars`, run `terraform apply`, then create their login profile (above).

## Tear down
`terraform destroy` in `envs/dev`. The database keeps a final snapshot (`unirise-dev-final`); delete it manually if you do not want it.

## Not done yet
- No ECS service, load balancer or deploy pipeline (the backend and its image exist; the ECS stage needs the VPC endpoints and the load balancer).
- No staging or production. Use separate AWS accounts for those and turn on Multi-AZ, deletion protection and stricter ECR tag rules.
- Domain: certificate and SES identity are in Terraform (`domain.tf`, off until `domain_name` is set); the DNS records are added by hand in Hostinger.
- CI builds and tests the API (`.github/workflows/api.yml`); there is no deploy job yet.
