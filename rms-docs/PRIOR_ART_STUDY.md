## 1. Per-system summaries (A–H), with sources

### VIVO (vivo-project/VIVO) + Vitro + VIVO-ISF ontology

VIVO is built on **Vitro**, a generic OWL-based semantic-web framework (Java/Tomcat), plus the **VIVO-ISF ontology** layered on top, derived from Dublin Core, BIBO, FOAF, SKOS and eagle-i/OBO BFO work ([Wikipedia — secondary source](https://en.wikipedia.org/wiki/VIVO_(software)); [Vitro GitHub — primary](https://github.com/vivo-project/Vitro); [ISF refactoring doc — primary](https://wiki.duraspace.org/download/attachments/34655727/refactoringForTheISF.pdf?api=v2)).

- **A. Data model:** Core entities `Person`, `Position` (incl. `FacultyPosition`), `Organization`, `Authorship`, `AdvisingRelationship` ([VIVO docs on Positions](https://wiki.lyrasis.org/x/CorVAw)). Effective dating uses reified role nodes (`Position`/`Authorship`/`AdvisingRelationship`) carrying a `DateTimeInterval`→`DateTimeValue` pair ([wiki](https://wiki.lyrasis.org/x/2JOoB)) — the one directly transferable pattern. No first-class joint-appointment entity (just two overlapping `Position`s) and **no documented mechanism for affiliation-at-time-of-publication** — flagged unverified/likely unmodeled.
- **B. Access control:** Four fixed roles pre-1.15; 1.15+ allows custom roles with per-class/per-property CRUD ([1.15.x docs](https://wiki.lyrasis.org/display/VIVODOC115x/Policies+defined+through+user+interface)). Critically, VIVO's own wiki warns to "never put any truly private data into VIVO" because hiding a field on the page doesn't hide it at the SPARQL endpoint — **visibility is UI suppression, not data security** ([wiki](https://wiki.lyrasis.org/x/tpIQAg)). No sensitivity tiers, no mentee-scoping, no org-tree rollup dashboards — VIVO ships only per-person visualizations ([example](https://experts.colorado.edu/vis/author-network/fisid_113318)).
- **C. Workflows:** VIVO Harvester pulls PubMed/Scopus ([wiki](https://wiki.lyrasis.org/x/BgUGAg)); a 2015 UNM study found default harvests "often inaccurately and incompletely populate" faculty lists ([study](https://scholarworks.iu.edu/iuswrrest/api/core/bitstreams/8e808901-ae2f-4759-b0f2-807ebdf846dd/content)). A 2019 ticket (VIVO-1415) added DOI/PMID claim UI ([commit](https://dev.litvinovg.pro/litvinovg/vivo/src/commit/f597b7ee427b5311f15b962acf3ab1eb3d741652)). **No dispute flow, approval sign-off, or period-locking/snapshot concept found anywhere** — confirmed negative finding.
- **D. Scholar progress:** Not modeled beyond a generic dated `AdvisingRelationship` ([1.14.x docs](https://wiki.lyrasis.org/display/VIVODOC114x/Advising+Model)). Even a Columbia Biomedical Informatics extension project confirmed they had to hand-build their own milestone classes ([PMC4005926](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC4005926/)).
- **E. Counting rules:** None found — out of scope for VIVO's expert-finding purpose.
- **F. Configurability:** Admins can add OWL classes/properties via the UI, but must avoid the core namespace to prevent upgrade collisions ([wiki](https://wiki.lyrasis.org/x/zIAQAg)) — real semantic-drift risk, documented at Columbia ([PMC4005926](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC4005926/)).
- **G. Integrations:** Real ORCID integration since a 2013 Cornell grant ([wiki](https://wiki.lyrasis.org/x/H72dB)). Crossref/OAI-PMH/SWORD/CERIF export are weak-to-absent: CERIF mapping exists only as a 2013 academic paper, not a shipped exporter ([paper](https://repository.mdx.ac.uk/item/89188)).
- **H. Weak points:** **No multi-tenancy** — every deployment is one self-hosted instance per institution ([JLSC article](https://iastatedigitalpress.com/jlsc/article/12802/galley/12501/view)). **License confirmed BSD-3-Clause** by direct inspection of the LICENSE file ([github.com/vivo-project/VIVO/blob/main/LICENSE](https://github.com/vivo-project/VIVO/blob/main/LICENSE)); Wikipedia's "Apache License" infobox is wrong/stale. Actively maintained: v1.16.0 released recently, 5,455 commits ([releases](https://github.com/vivo-project/VIVO/releases)).

### DSpace + DSpace-CRIS (4Science)

**Major finding, both systems:** DSpace governance approved a formal merger of DSpace-CRIS into core DSpace (Nov 2025), phased across DSpace 10.0 (first CRIS features absorbed, mid-2026) and 11.0 (full consolidation, targeted May/June 2027) ([merger approval announcement](https://dspace.org/?p=238272); [4Science announcement](https://dspace.org/dspace-and-dspace-cris-merger-4science-actively-supports-the-evolution-of-the-dspace-community/); [10.0 release notes](https://dspace.org/?p=238520)).

**DSpace:** BSD-3-Clause ([repo](https://github.com/DSpace/DSpace)), 25,480+ commits, DSpace 10.0 released May 28 2026 ([dspace.org](https://dspace.org/?p=238520)).
- **A.** Community→Collection→Item→Bundle→Bitstream ([Lyrasis wiki](https://wiki.lyrasis.org/x/_xL7AQ)). Since v7, optional "Configurable Entities" add Person/OrgUnit/Project/Publication via a generic Relationship model, disabled by default and needing a DB migration (`initialize-entities`) to turn on ([entities doc](https://wiki.duraspace.org/download/attachments/145555458/2-%20dspace-entities.pdf)). **No effective-dating found** on these relationships; author affiliation is a plain metadata string, not a time-bound link.
- **B.** Classic default-deny Resource Policies (action × object × EPerson/Group) ([community write-up](https://www.nsrc.org/workshops/2013/senegal-archives-uo/raw-attachment/wiki/References/dspace_autorizations.pdf)). No field-level visibility, no mentee/org-rollup concept.
- **C.** "Configurable Workflow" engine, step-based, since DSpace 7 ([Lyrasis wiki](https://wiki.lyrasis.org/display/DSDOC7x/Configurable%2BWorkflow)). No period-locking concept found.
- **D.** Not modeled — confirmed gap, expected given DSpace's repository/preservation purpose.
- **E.** None native to core.
- **F.** Configurable but developer-level (XML config + migration script), not self-service.
- **G.** SWORD v2 + OAI-PMH both standard ([comparison](https://casrai.org/compare/oai-pmh-vs-sword)). Native ORCID support is newer/thinner than CRIS's, with most integration only ported back in DSpace 7.3 ([wiki](https://wiki.lyrasis.org/x/mArXBw)).
- **H.** **No built-in multi-tenancy** — California State University had to build a custom config to run 17 instances on one server because stock DSpace doesn't support it; Texas Digital Library instead just runs one full install per institution ([Code4Lib discussion](https://wiki.code4lib.org/Special:MobileDiff/39886); [TDL](https://tdl.org/?p=26)).

**DSpace-CRIS:** Distributed as 4Science's fork, `github.com/4Science/DSpace` branch `main-cris`, BSD-3-Clause ([repo](https://github.com/4Science/DSpace)). No longer a standalone product — see merger finding above.
- **A.** Same entity model, but a community thread confirms a real limit: **"it's only possible to set just one affiliation per author" at publication level** — no proper time-boxed joint-appointment history ([community thread](https://wiki.lyrasis.org/x/M6o2BQ)). CERIF-exported affiliation elements do carry a `startDate`, but no end-date or appointment-history UI was confirmed.
- **B.** The strongest access model in this survey: (1) tab/box-level profile-page visibility, (2) metadata-field "security levels" (level 0 = public, most-specific-wins, configurable in `metadata-security.cfg`), (3) per-value "restricted" overrides, (4) whole-entity "Private" flag ([DSpace 10.x metadata security doc — primary](https://wiki.lyrasis.org/spaces/DSDOC10x/pages/438698074/Metadata+security+configuration); [4Science slide deck — vendor marketing, secondary](https://www.slideshare.net/4Science/dspacecris-technical-level-introduction)) — maps well onto RMS's public/internal/confidential tiers.
- **C.** Same workflow engine, plus ORCID-based profile claim + optional "ORCID Push" ([institutional help page example](https://research.matf.bg.ac.rs/help/orcid-documentation.jsp)). No period-locking workflow found.
- **D.** Not modeled as a product feature; some institutions misuse it as a thesis repository instead ([Novi Sad example](https://open.uns.ac.rs/handle/123456789/1953)).
- **E.** Real bibliometrics layer (Scopus/WoS/PubMed, Altmetric/PlumX, journal IF/h-index) ([Lyrasis wiki](https://wiki.lyrasis.org/x/S62oB)); no documented double-counting-across-departments logic.
- **F.** Same config cost as DSpace plus the 3-layer security config overhead.
- **G.** Mature CERIF-over-OAI-PMH export (since DSpace-CRIS 5.5.1, ~2016); CERIF **import** maturity unverified/possibly incomplete ([wiki](https://wiki.lyrasis.org/x/JQZxB)). Strong ORCID.
- **H.** Same multi-tenancy gap. **Being discontinued as a standalone product line, folded into DSpace core by ~2027** ([governance announcement](https://dspace.org/?p=238272)) — the single most important weak point for treating it as a stable reference today.

### OSIRIS (OSIRIS Solutions GmbH, Germany)
*Disambiguation: unrelated to the Dutch student-records "OSIRIS." Confirmed real via its own GitHub org and wiki ([GitHub](https://github.com/OSIRIS-Solutions/osiris); [wiki](https://wiki.osiris-app.de); [EasyChair CRIS2026 paper](https://easychair.org/publications/paper/Pjkg/open)).*
- **A.** Activities/Projects/Persons/Org-units (nestable, with "time-resolved links" for membership)/Journals/Infrastructures/Events ([wiki nav](https://wiki.osiris-app.de)). Exact joint-appointment/affiliation-at-publication semantics unverified.
- **B.** Five fixed roles (User/Scientist/PA/Editor/Admin), fixed rights bundles ([roles doc](https://wiki.osiris-app.de/en/admins/user_roles/roles/)). No field-level visibility or org-rollup dashboard found.
- **C.** Optional "Quality workflows" module (≥v1.6.0) for configurable approval chains per activity type ([doc](https://wiki.osiris-app.de/en/admins/workflows/workflows/)) — real precedent for optional per-type approval. A claim flow exists (per-item or bulk) ([claiming doc](https://wiki.osiris-app.de/en/users/profile/claim_activity/)). No dispute/period-locking found.
- **D.** Not modeled — pure activity/output tracker.
- **E.** A "duplicates" API endpoint exists; KDSF 2.0 (German core dataset standard) referenced, but its page is under construction ([interfaces doc](https://wiki.osiris-app.de/en/topics/interfaces/)).
- **F.** Custom fields/vocab/keywords admin-configurable.
- **G.** ORCID, Crossref/DataCite DOI, PubMed ID, OpenAlex, Google Scholar, LDAP, OAuth2 ([interfaces doc](https://wiki.osiris-app.de/en/topics/interfaces/)). No OAI-PMH/SWORD/CERIF found.
- **H.** MIT license ([GitHub](https://github.com/OSIRIS-Solutions/osiris)), actively maintained (releases 1.8.1→2.1.0 recently). Docs only ever discuss "your institution" (singular) — likely single-tenant, not explicitly confirmed either way.

### Haplo Research Manager (Haplo Services Ltd → acquired by Cayuse, Jan 2021)
- **A.** Generic linked-data object-store platform; `haplo-research-manager` repo folder names indicate researcher profiles, projects, publications, identifiers (ORCID/GRID/HESA/DOI/Handle) ([GitHub](https://github.com/haplo-org/haplo-research-manager)) — inferred from repo structure, not a documented ERD. Effective-dating/joint appointments: unverified.
- **B.** Platform uses "label-based permissions" ([GitHub — primary](https://github.com/haplo-org/haplo)). The Graduate Education Manager (PGR) module has a named "Haplo Postgraduate Researcher" role; a Cayuse support article title ("Standard Role Configurations") suggests role-continuity handling when a holder is away, but the article itself 403'd on direct fetch — this is inferred from the page's title/snippet in search results, not from reading the article, so treat it as plausible, not confirmed ([Cayuse support article — unconfirmed, fetch blocked](https://support.cayuse.com/hc/en-us/articles/50895071745939-Graduate-Education-Manager-Standard-Role-Configurations)).
- **C.** Separate modules per function: Ethics Monitor (ethics application administration — [support.haplo.com/ethics-monitor](https://support.haplo.com/ethics-monitor)); funding pre/post-award; repository. *(Note: an earlier draft of this section cited a specific Edge Hill ethics-process detail against a bare Google search URL, which is not a real source — that specific claim is withdrawn and treated as unverified.)* Approval chains, period locking, dispute handling: not found in public sources.
- **D. The strongest finding in this study — but confirmed only at the "a paid product like this exists" level, not at the feature-detail level.** What's solid: Haplo/Cayuse sells a dedicated PhD-progress module (originally "PhD Manager," now **Graduate Education Manager**), and multiple UK universities' own pages describe it in terms of milestone tracking and reminders — e.g. London South Bank University's own description: "gives an accurate, comprehensive and up-to-date record of progress on your research project, and alerts you to milestones." What's *not* independently confirmed: the specific claims that it sends reminders to **both** student and supervisor, and that a role holder's absence doesn't break the workflow. Every page that would confirm those two specifics — `support.haplo.com/phd-manager/administrators/project-dates`, the LSBU page itself, and the Cayuse role-configuration article in B below — returned a 403 or redirected to an authenticated Cayuse support portal on direct fetch; what's quoted here comes from search-engine snippets of those pages, not a page actually opened and read. Treat "a real paying market for PhD-milestone tracking exists" as confirmed, and "dual reminders + role continuity, specifically" as plausible but unconfirmed pending either a login to Cayuse's support portal or a direct vendor/customer conversation. Supervision-meeting-note storage is indicated at Southampton/Open University but **the meeting-log structure itself is unverified** — those pages also required authenticated access.
- **E.** Not documented.
- **F.** Server-side JS plugin API (`haplo-plugin-tool`) — developer-level configurability, not an admin UI like OSIRIS's; inferred, not directly documented for Research Manager specifically.
- **G.** ORCID push/pull ([Cayuse article](https://support.cayuse.com/hc/en-us/articles/28264503310739-Researchers-ORCID-ID-Integration)); OAI-PMH confirmed for the Repository module including an EThOS/British-Library translation ([Haplo release notes](https://www.haplo.com/news/haplo-repository-open-source-release)); DataCite DOI minting ([CoSector](https://cosector.com/?p=488)). SWORD/CERIF: not found.
- **H.** License split: the underlying Haplo Platform and `haplo-research-manager` plugin repo are both **MPL-2.0** ([GitHub](https://github.com/haplo-org/haplo); [GitHub](https://github.com/haplo-org/haplo-research-manager)). But the product *sold today* is closed, vendor-hosted under Cayuse; **UK G-Cloud pricing lists ~£110,000/instance/year** plus onboarding fees scaled to an institution's research grant income ([Digital Marketplace listing](https://www.applytosupply.digitalmarketplace.service.gov.uk/g-cloud/services/418430553303165); [pricing PDF, dated 2022/2023 — may be stale](https://assets.applytosupply.digitalmarketplace.service.gov.uk/g-cloud-13/documents/711691/761034067613108-pricing-document-2023-10-10-1421.pdf)). Public `haplo-research-manager`/`haplo-repository` repos show **no commits since June 1, 2021** — development has visibly moved to a private Cayuse fork.

### Profiles RNS (Harvard Catalyst origin)
- **A.** Person "electronic CV" (publications from PubMed, education, awards/grants, NIH concept tags) linked via a "Disambiguation Engine" matching HR/directory data against PubMed by name/email/affiliation/co-author signals ([UF Health](https://support.webservices.ufhealth.org/2022/06/22/how-the-directory-finds-publications-for-your-profile/); [Harvard Catalyst](https://catalyst.harvard.edu/informatics/open-source-software/profiles-rns)). Department affiliation appears to be a flat Person attribute — effective-dating/joint appointments unverified, not found in any source reviewed.
- **B.** Faculty self-administer their profile and can grant "proxy" edit access; department admins are auto-provisioned as proxies but cannot grant proxy access on a faculty member's behalf ([Harvard Catalyst wiki](https://harvardwiki.atlassian.net/wiki/x/nZVkAw)). No field-level visibility, rollup dashboard, or formal RBAC documented.
- **C.** Claim/verify is the core workflow: the Disambiguation Engine proposes PubMed IDs; researchers/proxies accept, search-add, or manually add, and **the engine learns from corrections** ([Rush University](https://www.rushu.rush.edu/research-rush-university/resources-researchers/data-management/profiles-research-networking)). No dispute/approval/period-locking documented.
- **D.** Not present in any source reviewed.
- **E.** Not documented.
- **F.** Institutions (UCSF, UC Davis, UC Irvine, Rush, BU, Colorado) run customized forks/skins rather than configuring a shared schema — e.g. UCSF's "ORNG" add-ons ([Harvard Catalyst](https://catalyst.harvard.edu/informatics/open-source-software/profiles-rns)) — the cost of flexibility here is "maintain your own fork."
- **G.** PubMed for publications, NIH ExPORTER for grants ([Harvard Catalyst](https://catalyst.harvard.edu/informatics/open-source-software/profiles-rns)); ORCID via the Crossref API ([UF Health](https://support.webservices.ufhealth.org/2022/06/22/how-the-directory-finds-publications-for-your-profile/)); modeled in the VIVO ontology, exposed via RDF/XML, SPARQL, and an XML Search API ([UCSF](https://profiles.ucsf.edu/About/?tab=data)). No OAI-PMH/SWORD found.
- **H.** Single-tenant per deployment (inferred, not explicit). Legacy stack: C#/.NET, MS SQL Server, IIS ([Harvard Catalyst](https://catalyst.harvard.edu/informatics/open-source-software/profiles-rns)). License BSD-3-Clause core, bundled components MIT/Apache-2.0 ([GitHub](https://github.com/ProfilesRNS/ProfilesRNS)). Still actively maintained (commits as recent as October 2026) despite a stale-looking marketing page.

### Kuali Coeus / Kuali Research (integration-boundary analysis only)
- **A.** Proposal Development → Institutional Proposal (internal approval) → Award, data "pulled forward" at each stage; Subaward pulls forward from Award ([UMD ORA](https://ora.umd.edu/node/160); [UCSD](https://esr.ucsd.edu/projects/kuali-research/about/index.html)). Person/unit data is **not** natively authored in Kuali — fed in daily from the institution's HR system (e.g. PeopleSoft) ([UMD](https://ora.umd.edu/node/160)) — matches RMS's own non-goal of not being an HR system of record. No explicit effective-dating fields confirmed on person/unit records; the forward-pull pattern is the clearest documented "snapshot" mechanic.
- **B.** Group-based access permissions exist ([Kuali release notes](https://announcekit.app/kuali/announcements/date/2025/11)); no detailed role/field-visibility model found.
- **C.** Proposal→Institutional Proposal is an internal sign-off gate before submission ([UMD](https://ora.umd.edu/node/160)); compliance workflows (IRB/IACUC/COI) run as separate linked products ([CASRAI comparison](https://casrai.org/compare/cayuse-vs-kuali)).
- **D./E.** Not applicable — sponsored-programs/compliance software, not a progress tracker or output-counting tool.
- **F.** Not well documented publicly.
- **G. The focus question — and the biggest gap found.** Current institutional practice is manual UI-level "Export List" (CSV/XML) for Proposal/Award data, not a documented developer API ([UMBC](https://research.umbc.edu/accessing-your-kuali-data/); [MIT quick reference](https://kc.mit.edu/document/kuali-coeus-institutional-proposal-quick-reference-v2-dec-2019)). UMBC's own research office states it is *still working with Kuali* to pipe data into a separate data warehouse ([UMBC](https://research.umbc.edu/accessing-your-kuali-data/)). **No official Kuali developer/API documentation was locatable anywhere in this research.** Confirm directly with KualiCo or a pilot customer before designing any integration against it.
- **H.** Originally Educational Community License v2.0 under the nonprofit Kuali Foundation ([OpenHub](https://openhub.net/p/kuali-coeus)); governance moved to commercial KualiCo in 2014, which kept multitenant SaaS features proprietary/closed while already-released code stayed open ([eliterate.us, "Kuali and Open-Washing" — opinion blog, secondary](https://eliterate.us/kuali-guilty-open-washing/)). Today, **Kuali Research is sold as quote-priced closed SaaS** ([G2 pricing page — user-review aggregator, secondary](https://www.g2.com/products/kuali-research/pricing)) — effectively closed/commercial, not forkable. Actively maintained: monthly release notes through Jan 2026, a 2026 platform migration planned ([SFU](https://www.sfu.ca/main/research/researcher-resources/plan-my-research/research-systems/kuali-nextgen.html)).

### CERIF (euroCRIS) + OpenAIRE Guidelines (standards, not software)
- **A. The most valuable finding for RMS's own schema.** CERIF's base entities (Person, OrganisationUnit, Project, plus result entities `cfResultPublication`/`cfResultProduct`/`cfResultPatent`/`cfFunding`/etc.) carry almost no attributes themselves. Nearly everything meaningful is expressed via **link entities pairing two base entities with a role + start date + end date** — e.g. `cfPers_OrgUnit` (role: "employee"/"head of department"), `cfPers_Project` (role: "principal investigator"/"PhD student") ([UKOLN CERIF intro](https://www.ukoln.ac.uk/rim/documents/Introduction_to_CERIF_1.0.pdf); [CERIF entity vocab](https://cerif.eurocris.org/vocab/html/CERIFEntities.html); role vocab files for [Person-OrgUnit](https://cerif.eurocris.org/vocab/xml/PersonOrganisationRoles.xml) and [Person-Project](https://cerif.eurocris.org/vocab/xml/PersonProjectEngagements.xml)). This independently confirms RMS's `appointment`/`role_grant`/`relationship` design is the right shape. Notably, **CERIF models "PhD Student" as a role tag on a Person↔Project link, not a distinct entity** — RMS's dedicated `milestone`/`relationship` tables are a deliberate improvement on this for a product where PhD progress is a core feature.
- **B.** Confirmed out of scope by direct inspection — the OpenAIRE CRIS implementation guidelines have no access-rights/visibility section at all ([guidelines.openaire.eu/cris/implementation](https://guidelines.openaire.eu/en/latest/cris/implementation.html)). The separate Literature Repository Guidelines define per-record Access Level/License/Embargo fields, but that's open-access status, not a role/permission model ([guidelines v3.0.1](https://guidelines.openaire.eu/en/latest/literature/introduction.html)).
- **C.** No standardized approval/status state machine in CERIF itself — "status" is just an open classification tag ([OpenAIRE CRIS elements page](https://acz-guidelines-cris-managers.readthedocs.io/en/latest/cris_elements_openaire.html)). OpenAIRE's own **deduplication** (candidate clustering → decision-tree classifier on title+year+author-string, with user feedback fed back in) is real, documented prior art for cross-repository duplicate detection ([OpenAIRE blog](https://beta.openaire.eu/blogs/on-deduplication-in-the-openaire-infrastructure-1)).
- **D.** No dedicated qualification/CV entity; "PhD Student" is a `cfPers_Project` role tag only (see A). A `cfPers_Pers` link entity exists for person-to-person professional relationships, but no confirmed named "Supervisor/Advisor" term — that specific vocabulary page failed to load directly, so flagged unverified.
- **E.** Open classification-scheme layer: anything taggable via a `cfClassificationScheme`/`cfClassId` pair, with CERIF deliberately not fixing which vocabularies must be used; OpenAIRE's profile then mandates specific ones (e.g. COAR Resource Types) on top ([OpenAIRE CRIS elements page](https://acz-guidelines-cris-managers.readthedocs.io/en/latest/cris_elements_openaire.html)). No CERIF/OpenAIRE guidance found on cross-institution credit-splitting/double-counting — confirmed out of scope for both standards.
- **F.** Highly extensible by design — new concepts become classified links rather than schema changes ([UKOLN CERIF intro](https://www.ukoln.ac.uk/rim/documents/Introduction_to_CERIF_1.0.pdf)).
- **G.** Concrete, well-documented export target: **CERIF-XML 1.6 over OAI-PMH**, metadata prefix `oai_cerif_openaire`, with mandatory per-entity sets ([guidelines.openaire.eu/cris/implementation](https://guidelines.openaire.eu/en/latest/cris/implementation.html)). ORCID/ROR are *not* mandated in the pages reached — treat as unverified whether a newer guidelines version requires them.
- **H.** Maintained by euroCRIS (nonprofit) since 2000–2002 (sources disagree on exact year) ([euroCRIS history](https://eurocris.org/node/1111)). Stable reference is CERIF 1.5 (2014) per the EU's Interoperable Europe catalogue ([catalogue](https://interoperable-europe.ec.europa.eu/collection/eu-semantic-interoperability-catalogue/solution/common-european-research-information-format)); a secondhand, unverified claim suggests "classic" CERIF may be giving way to an experimental "CERIF-Core" successor — explicitly flagged unconfirmed in the original research and still unconfirmed here. OpenAIRE Guidelines for CRIS Managers v1.2.0 (2023) are confirmed current ([Zenodo](https://zenodo.org/records/8050936)). EU-centric origin (IDEAS project, 1980s) ([Interoperable Europe catalogue](https://interoperable-europe.ec.europa.eu/collection/eu-semantic-interoperability-catalogue/solution/common-european-research-information-format)) — not immediately relevant to a non-EU first market for compliance purposes, though the data-modeling patterns are market-agnostic. ## 3. Borrow / adapt / avoid

**Borrow**
- **CERIF's role+time link-entity pattern** → confirms TRD §4 "Planned additions" (`researcher_affiliation`) and ACCESS §5 (`appointment`, `role_grant`, `relationship` tables) are the right shape. Validation, not new work.
- **DSpace-CRIS's 3-layer visibility resolution** (page/tab → field security level → per-value override → entity-private, most-specific-wins) → adopt this exact resolution order for ACCESS §5's visibility-check algorithm for public/internal/confidential tiers.
- **Haplo's PGR milestone-engine** → direct implementation model for ACCESS §7 decision 7 and FRONTEND_SPEC's future Review-queue/reminder screens — a real paying market for this category is confirmed. The specific "sends to both student and supervisor" detail is plausible (per section 1's Haplo/D entry) but rests on a search snippet of a page that 403'd, not a confirmed read — worth designing as the sensible default regardless, just don't cite Haplo as proof of that exact mechanic in a pitch deck without re-checking it.
- **Haplo's apparent "role continuity if holder is away"** → same caveat: the source is a support-article title, not its confirmed content. The underlying idea (a delegate/backup-supervisor concept on `relationship`, for ACCESS §6's "supervisor leaves, scholars left without one" edge case) is worth adopting on its own merits — RMS needs it either way — just don't present Haplo as having proven this works.
- **OSIRIS's "approval workflow optional per activity type"** → reinforces ACCESS §7 decision 6 (HoD validation optional per tenant) as standard industry practice.
- **Kuali's forward-pull snapshot chain** (Proposal→Award copies data forward at each stage) → adopt for ACCESS §4 step 6 ("close the period and freeze a snapshot"): materialize a copy at period-close rather than only computing reports live.
- **OpenAIRE's dedup technique** (cluster candidates, classify by title+year+author-string, feed back user confirm/reject) → directly informs TRD §6 matching logic — confirms the fuzzy title+year+surname approach already planned is industry-standard.
- **CERIF's open classification-scheme layer** → adopt a generic `classification_scheme`/`classification_term` table instead of hardcoded enums, for ACCESS §6's "journal quality lists change over time" edge case.

**Adapt**
- **VIVO/Profiles RNS's claim-and-learn disambiguation loop** → RMS's planned claim workflow (R12) is already similar; adapt by adding Profiles RNS's "learns from corrections" feedback loop into the matching-score system (TRD §6).
- **CERIF's "PhD Student" as a role tag, not an entity"** → RMS's richer, dedicated milestone/relationship model is better suited to a product where PhD progress is core — don't downgrade to CERIF's genericness, but note the tag-based approach is enough for a future CERIF-XML export if ever needed.

**Avoid**
- **VIVO's "visibility is UI suppression, not data security"** mistake → RMS's TRD §3 already states authorization is "checked in service layer, not only at controllers" — keep that discipline.
- **DSpace-CRIS's single-affiliation-per-publication limitation** → RMS's ACCESS §6 already plans affiliation-at-publication-date via effective-dated appointments; confirmed as a real, easy-to-get-wrong gap other shipped systems have — don't simplify it away later.
- **VIVO's free-form ontology extensibility** (admins add arbitrary OWL classes) → causes semantic drift and painful upgrades (confirmed at Columbia). Prefer RMS's more constrained extension points (classification schemes, defined custom fields).
- **Treating DSpace-CRIS as a stable long-term reference** → it's being merged into core DSpace by ~2027; re-check its post-merger state before citing current DSpace-CRIS docs in any future decision.
- **Assuming Kuali exposes a usable API** → no confirmed Kuali Research award/grant API was found; treat Kuali as CSV/manual-export-only in TRD §5 integration planning (R16) until directly confirmed otherwise with a customer.
